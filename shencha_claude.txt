  二、新发现问题

  N1（P1·完整性）分块上传（uploads 会话）没有字节区间覆盖校验 —— #57 只修了 multipart 路径。 UploadChunk 只累加 UploadedSize计数，CompleteUpload 只校验计数相等（service.go 第 365 行）。客户端对两个不同 chunk 写了同一 offset 时，计数达到 TotalSize 但预分配文件里留有零填充空洞——不带 hash 的上传会静默接受损坏文件。multipart 的 coveredRanges 机制应同样应用到这条路径。

  N2（P1·可用性）chunk/part 重试会永久毁掉会话。 网络重试是常态（响应丢失后客户端重发同一分块），但重发会使计数重复累加：
  - uploads 路径：UploadedSize 超过 TotalSize，CompleteUpload 的相等性检查永远失败；若重发时 offset+len > TotalSize 还会直接被拒。
  - multipart 路径：uploadedSize 双倍计数，CompleteMultipartUpload 第 271 行 totalUploaded != session.TotalSize 先于覆盖检查失败——尽管coveredRanges 明明能证明数据完整。

  multipart 修复很直接：完成时用 coveredRanges 推导已上传字节数，替代原始计数做相等性判断。

  N3（P2·多实例）启动时误删同主机其他实例的临时目录。 main.go 第 182–191 行无条件删除 os.TempDir() 下所有 fsserver-uploads-*目录。同一台机器跑两个实例时，后启动的实例会删掉先启动实例正在使用的上传临时目录，导致其所有进行中的会话写入失败。

  N4（P2·运维）/health 和 /ready 也经过并发限流中间件。 setupRoutes 里 concurrencyMiddleware 通过 engine.Use 全局注册（第 124 行），先于健康检查路由。服务器满载时探针拿不到信号量返回 503，Kubernetes会把高负载实例判定为不健康并重启——恰好在最不该重启的时候放大故障。健康检查应绕过该信号量。

  N5（P2·审计）gRPC 侧完全没有审计日志。 HTTP 的上传/删除/重命名等写操作都有 auditLog，gRPC 的同类RPC（UploadFile、DeleteFile、DeleteDirectory 等）一条都不记。同一操作经由不同协议审计覆盖不一致。

  P3 级别问题（列出供选择性处理）：
  - 上传/multipart 会话无属主绑定：任何通过认证的用户凭 sessionID 即可向他人会话写数据、complete 或 abort（sessionID 是 UUID难以猜测，风险低）。
  - JWT refresh 黑名单是进程内 sync.Map：多实例间旧 refresh token 可在其他实例重放；重启后黑名单清空。Redis 已可用时可下沉到 Redis。
  - 跨实例断点续传的两处不一致：会话每 8 个 chunk 才同步一次 Redis，另一实例执行 Complete 时 UploadedSize 可能过期而误报incomplete；加密下载会话被另一实例从 Redis 恢复后 decryptedFile 为 nil，会直接从存储读出密文返回给客户端（service.go DownloadChunk 第 692–704 行）。
  - GET /uploads/:id/progress 对不存在的会话返回 200 + uploaded_bytes: 0，应返回 404。
  - gRPC 指标 statusCodeFromErr 只区分 200/500，丢失了 NotFound/InvalidArgument 等分类；grpc/server.go 末尾的 computeNewPath 是死代码。
  - JWT 签名密钥仍与 defaultApiKeyHash 同值（hashApiKey(apiKey)），#65当时只改了注释；建议按注释所述做域分离（hashApiKey("jwt:"+apiKey)），注意这会使已签发 token 失效。
